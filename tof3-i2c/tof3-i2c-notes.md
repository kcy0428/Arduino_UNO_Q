# ToF 3 I²C — 속도/정확도 방향성 + 연결·데이터 취득 참고자료

네 가지를 정리합니다.

1. **진행 상황 요약** — 지금까지 뭘 확인하고 뭘 바꿨는지, 시간 순 타임라인.
2. 레인징 주파수(5 Hz)를 올리면 통신 오류가 줄고 값이 정확해질지 — 보드에 설치된
   드라이버 소스(`STM32duino VL53L8CX 2.1.0`)를 직접 확인해서 방향을 잡습니다.
3. 센서 3개가 MCU 포트에 어떻게 물리적으로 연결되고, `sketch.ino`가 어떤 순서로
   8×8 프레임을 실제로 읽어내는지 — 코드 줄 번호를 인용한 참고자료입니다.
4. **전원(전류/GND) 문제 진단** — 버스를 분리해도 남는 불안정이 왜 전원 쪽을
   가리키는지, 로그 근거와 확인·해결 방법.

**남은 선택지 (사용자 결정 대기)**:
1. 외부의 넉넉한 3.3V 전원으로 센서 레일 교체 (UNO Q 3.3V와 병렬 연결은 금지 — 두 레귤레이터를 직접 묶으면 역전류로 오히려 더 불안정해지거나 고장 위험)

3. 고속 충전기로 USB 입력 전류 여유 확보 (결과 대기 중)

## 1부. 5 Hz를 올리면 나아질까

### 1.1 "통신 속도"는 사실 서로 다른 두 값입니다

| 이름 | 코드 위치 | 현재 값 | 의미 |
|---|---|---|---|
| I²C 버스 클럭 | `sketch/sketch.ino:208` `Wire.setClock` / `:210` `Wire2.setClock` | `Wire`(센서 1·2) **100 kHz** · `Wire2`(센서 3) **400 kHz**(§1.4-4) | SDA/SCL 신호가 얼마나 빨리 토글되는지 |
| 레인징 주파수 | `sketch/sketch.ino:164` `vl53l8cx_set_ranging_frequency_hz(&sensor.device, 5)` | 5 Hz | 센서가 초당 몇 프레임을 만들어내는지 |

"5 Hz"는 후자입니다. 둘은 독립적인 값이고, 서로 다른 이유로 조정합니다.

### 1.2 지금 5 Hz는 이미 한계의 1/3만 쓰고 있습니다

드라이버 헤더 원문(`vl53l8cx_api.h`, `vl53l8cx_set_ranging_frequency_hz` 문서):

> For 4x4, min and max allowed values are : [1;60]
> For 8x8, min and max allowed values are : [1;15]

`sketch.ino`는 8×8 해상도(`VL53L8CX_RESOLUTION_8X8`, 64존)를 쓰므로 허용 범위는
1–15 Hz이고, 지금 설정된 5 Hz는 그 1/3입니다. 즉 "속도가 느려서" 문제가 나는
상태가 아니라 여유를 가진 상태입니다.

### 1.3 Hz를 올리는 건 오류를 줄이는 방향이 아니라 늘리는 방향에 가깝습니다

이전에 실제 보드 로그로 확인한 오류 패턴(연결 자체는 100% 성공 — `checking`
단계의 "No sensor at default/assigned address" 오류가 0건 — 이후
`start_ranging`/`data-ready`/펌웨어 업로드 같은 큰 I²C 트랜잭션 도중에만
코드가 1·3·133·255처럼 들쭉날쭉하게 실패)은 배선/풀업/전원 쪽 신호 품질
문제의 전형적인 모양입니다. 이 상태에서 Hz를 올리면:

- 초당 I²C 트랜잭션 횟수가 늘어나 **같은 배선 상태에서 오류를 만날 기회만
  늘어납니다.** 세 센서가 공유하는 버스라 부담은 3배로 커집니다.
- 8×8 해상도에서 Hz를 올리면 프레임당 적분 시간(integration time)이
  짧아져 **개별 프레임의 신호 대 잡음비가 낮아집니다.** "정확한 값"을 원하신다면
  오히려 반대 방향입니다 — 정확도는 갱신 빈도가 아니라 적분 시간·해상도가
  결정합니다.

**결론: 지금 상태에서 Hz를 올리는 건 통신 오류를 줄이는 해법이 아닙니다.**

### 1.4 권장 순서

1. **하드웨어 신호 품질부터 고정** — 이전에 드린 체크리스트: 풀업 저항, 공통
   GND/전원 품질, 배선 길이/접점, 센서 3↔센서 2 위치 스왑 테스트로 "모듈
   불량 vs 배선 구간 문제" 구분.
2. 아래 명령으로 오류율을 0에 가깝게 확인한 뒤에만 다음 단계로:
   ```sh
   arduino-app-cli app logs /home/arduino/ArduinoApps/tof3-i2c --tail 3000 \
     | grep -oE "\[ToF [0-9]\] error: [A-Za-z ]+" | sort | uniq -c | sort -rn
   ```
3. **그 다음에만, 단계적으로** Hz를 올려보기: 5 → 8 → 10 Hz처럼 조금씩,
   매 단계 후 위 명령으로 오류율을 다시 측정. 8×8의 상한인 15 Hz를 넘기지
   말 것 — `vl53l8cx_set_ranging_frequency_hz`는 범위를 벗어나면 상태 코드
   127을 반환하도록 문서화되어 있습니다.
4. **I²C 클럭(100 kHz → 400 kHz Fast Mode)은 별도 레버입니다.** 트랜잭션
   자체를 짧게 만들어 버스 점유 시간을 줄여주지만, 풀업/배선이 약한
   상태에서는 더 빠른 신호 엣지가 오히려 노이즈에 더 민감해집니다. 반드시
   1번(하드웨어 안정화) 이후에만 시도하세요.

   > **적용 기록**: 두 단계를 거쳤습니다.
   > 1. 처음엔 `Wire`(당시 세 센서 전부)를 400 kHz로 올렸는데, 하드웨어
   >    안정화(풀업 정리·버스 분리) 이전이라 오류가 계속 났습니다.
   > 2. 이후 센서 3을 `Wire2`(A4/A5)로 분리(§2.1) — 재배선 후 센서 3은
   >    오류 0건으로 완전히 안정됐지만, 센서 1·2가 공유하는 `Wire`는
   >    여전히 풀업 두 개(1008Ω·1017Ω 병렬 ≈ 509Ω)가 겹친 채라 계속
   >    `Data-ready read failed` 등으로 끊겼습니다.
   > **현재 상태**: `Wire`(센서 1·2)는 100 kHz로 되돌렸고(`sketch.ino:208`),
   > `Wire2`(센서 3, 이미 안정적)만 400 kHz 유지(`sketch.ino:210`)합니다.
   > 그래도 `Wire`가 계속 불안정하면, 다음은 저항 제거(센서 1·2 중 하나만
   > 풀업 남기기)가 남은 선택지입니다 — 위 §풀업 확인 방법 참고.
5. **Hz를 건드리지 않고 "정확도"를 올리는 방법**도 있습니다: 이미
   `sendFrame()`(`sketch.ino:177`)이 `target_status`가 5 또는 9일 때만
   거리를 채택하는 필터가 들어가 있는데, 여기에 더해 Python
   쪽(`python/main.py`의 `on_frame`)에서 존별로 최근 N프레임 이동평균/median을
   유지하면 갱신 속도를 안 올려도 화면에 보이는 값의 흔들림을 줄일 수 있습니다.

## 2부. 센서 3개 ↔ MCU 연결, 8×8 데이터 취득 과정

### 2.1 물리적 연결

> **업데이트(풀업 확인 후)**: 실측 결과 센서 3보드 각각 자체 풀업(1.0~1.24kΩ)을
> 갖고 있어 셋을 한 버스에 합치면 병렬로 겹쳐 ~360Ω까지 내려가는 게 확인돼,
> 센서 3을 별도 I²C 버스(`Wire2`, A4/A5)로 분리했습니다(`sketch.ino:14, 97-106,
> 207-210`). 아래 표·설명은 이 변경을 반영한 현재 구조입니다.

| 센서 | LPn 핀(개별) | I²C 버스 | SDA/SCL | 기본 I²C 주소 | 부팅 후 지정 주소 |
|---|---|---|---|---|---|
| 센서 1 | D2 | `Wire` (i2c2) | D20 (SDA) / D21 (SCL) | 0x29 | **0x30** |
| 센서 2 | D3 | `Wire` (i2c2) | 〃 | 0x29 | **0x31** |
| 센서 3 | D4 | `Wire2` (i2c3) | A4 (SDA) / A5 (SCL) | 0x29 | **0x32** |

센서 1·2는 SDA/SCL/전원/GND를 공유하는 **하나의 버스**(`Wire`)에 물려 있어
서로 구분하려면 LPn이 반드시 필요합니다. 센서 3은 **완전히 별도의 버스**
(`Wire2`)에 혼자 있어서 주소가 겹칠 상대가 없지만, 전원 on/off 제어와
`fail()`의 재연결 로직을 나머지 두 센서와 동일하게 쓰기 위해 LPn(D4)은
그대로 사용합니다. LPn이 LOW면 그 센서는 자기 버스에서 완전히 분리됩니다
(응답하지 않음) — `sketch.ino:202-205`에서 부팅 시 셋 다 LOW로 시작하는
이유입니다.

> **세 번째 버스는 없습니다**: 칩에는 `i2c4`라는 세 번째 I²C 주변장치가
> 더 있지만, 디바이스트리 확인 결과 그 핀(기본 PD12/PD13, 대체 PF14/PF15)은
> 일반 헤더(D0~D13/A0~A5/D20~D21)로 안 나와 있습니다 — PD12/PD13은 목록에
> 아예 없고(온보드 카메라 커넥터용으로 추정), PF14/PF15는 있긴 하지만
> "JMISC"라는 별도 내부 확장 커넥터 소속이라 점퍼선으로 바로 쓰기 어렵습니다.
> 그래서 센서 1·2는 계속 `Wire`를 같이 써야 하고, 남은 개선 수단은 풀업
> 정리(§풀업 확인 방법)입니다.

코드에서 어느 센서가 어느 버스를 쓰는지는 `sketch.ino:14`의
`SENSOR_BUS[] = {&Wire, &Wire, &Wire2}` 한 줄로 정해지고, `writeSensor`/
`readSensor`(`sketch.ino:41-74`)가 `handle`로 넘어온 `SensorState*`에서
`sensor->bus`를 읽어 그 버스로 I²C 트랜잭션을 보냅니다 — 드라이버(ST API)가
호출하는 경로와 스케치가 직접 호출하는 경로 모두 항상 `&sensor`(해당
센서의 `SensorState*`)를 handle로 넘기도록 통일돼 있습니다.

### 2.2 부팅 시 주소 지정 (`setup()` → `connectSensor()`)

모든 VL53L8CX는 전원이 들어오면 기본 주소 `0x29`로 켜집니다. **같은 버스를
쓰는 센서끼리**(지금은 센서 1·2만) 동시에 올리면 주소가 겹치므로, LPn으로
한 번에 한 센서만 버스에 연결해서 순서대로 주소를 바꿉니다. 센서 3은 혼자
쓰는 버스(`Wire2`)라 주소 충돌 걱정은 없지만, 코드는 세 센서 모두 같은
`connectSensor()` 절차를 순서대로 거칩니다.

```
setup()                                    sketch.ino:199-213
  ├─ 세 LPn 모두 pinMode(OUTPUT) + LOW      → 셋 다 각자 버스에서 분리
  ├─ Bridge.begin()
  ├─ Wire.begin() / setClock()              → 센서 1·2용 버스
  ├─ Wire2.begin() / setClock()             → 센서 3 전용 버스
  ├─ delay(BOOT_SETTLE_MS)                  → 센서 전원 안정화 대기
  └─ connectSensor(0), connectSensor(1), connectSensor(2)  순서대로 호출
```

`connectSensor(index)` 한 번의 내부 순서 (`sketch.ino:97-175`):

0. `sensor.bus = SENSOR_BUS[index]` — 이 센서가 어느 버스(`Wire`/`Wire2`)를
   쓸지 고정. (101행)
1. `digitalWrite(LPn_PINS[index], HIGH)` — 이 센서만 자기 버스에 올림.
   `delay(LPN_SETTLE_MS)`로 정착 대기. (112-113행)
2. `0x29`에서 ID 레지스터(뱅크 0, 레지스터 0-1)를 읽어 `0xF0/0x0C`인지 확인.
   실패하면 이미 이전에 주소가 바뀐 상태일 수 있으므로 `SENSOR_ADDRESSES[index]`
   (0x30/31/32)에서 다시 확인 — LPn은 칩을 리셋하지 않고 I²C만 끊기
   때문입니다. (115-127행)
3. 아직 기본 주소였다면 `vl53l8cx_set_i2c_address()`로 `0x30+index`로 변경,
   바뀐 주소에서 다시 ID를 읽어 확인. (139-155행)
4. `vl53l8cx_init()` — 센서 내부 펌웨어를 I²C로 업로드(수백 ms 소요, 가장 큰
   전송). (160행)
5. `vl53l8cx_set_resolution(VL53L8CX_RESOLUTION_8X8)` — 8×8 = 64존으로 설정.
   (162행)
6. `vl53l8cx_set_ranging_frequency_hz(5)` — 초당 5프레임. (164행)
7. `vl53l8cx_start_ranging()` — 연속 측정 시작. (166행)

각 단계가 실패하면 `fail()`이 그 센서의 LPn만 LOW로 내리고 `error` 상태로
전환하며, 나머지 두 센서는 영향받지 않습니다(§이전 답변에서 로그로 확인).
이제는 버스 자체도 분리돼 있어서(§2.1), 센서 3의 배선 문제는 물리적으로도
센서 1·2에 전달될 경로가 없습니다.

### 2.3 8×8 프레임을 실제로 읽어오는 루프 (`loop()`, `sketch.ino:215-236`)

세 센서를 매 반복마다 순서대로 처리합니다(단일 스레드, 순차 처리 — 버스가
분리돼 있어도 MCU 자체는 하나라 세 센서를 한 루프 안에서 차례로 돕니다):

```
for i in [센서1, 센서2, 센서3]:
    if !running:                       # 연결 안 된 센서
        3s 마다 connectSensor(i) 재시도
        continue
    vl53l8cx_check_data_ready()        # 새 프레임이 준비됐는지 폴링
    if !ready: continue                # 아직이면 다음 센서로 넘어감
    vl53l8cx_get_ranging_data(&result) # 준비됐으면 64존 결과 전체를 I2C로 읽음
    sendFrame(i)                       # Bridge로 Python에 전달
delay(10)
```

`vl53l8cx_get_ranging_data()`가 채우는 `VL53L8CX_ResultsData` 구조체 중
`sendFrame()`이 실제로 쓰는 두 배열(`vl53l8cx_api.h:342, 368`):

- `distance_mm[64]` — 존당 거리(mm). 인덱스는 `zone * VL53L8CX_NB_TARGET_PER_ZONE`
  (타깃 1개 모드이므로 사실상 `zone`과 동일).
- `target_status[64]` — 측정 신뢰도. **5 또는 9만 "유효한 레인징"** 을 의미
  (헤더 주석: *Status indicating the measurement validity, 5 & 9 means
  ranging OK*).

`sendFrame()`(`sketch.ino:177-197`)은 존마다 다음 조건을 만족할 때만 거리를
JSON에 싣고, 아니면 `null`을 넣습니다:

```cpp
bool valid = result.nb_target_detected[i] > 0 &&
             (status == 5 || status == 9) && result.distance_mm[n] >= 0;
```

완성된 프레임은 `{"seq": N, "distance_mm": [...64개...], "target_status": [...64개...]}`
JSON 문자열로 만들어 `Bridge.notify("tof3_frame", index, payload)`로 Python에
보냅니다 — `notify`라 fire-and-forget이고, MCU는 응답을 기다리지 않습니다.

### 2.4 Python·웹 쪽에서 받는 과정

- `python/main.py`의 `on_frame()`(6행 import한 `Bridge.provide`로 등록,
  36-59행 정의)이 `tof3_frame`을 받아 64개 길이·타입·범위를 검증하고
  `sensors[index]`에 저장합니다. 이름이 하나라도 다르면(`Bridge.provide`와
  `Bridge.notify`의 문자열) 조용히 무시되므로, MCU·Python 양쪽의 문자열이
  정확히 같아야 합니다.
- `snapshot()`이 `GET /api/status`(`arduino:web_ui` 브릭)로 세 센서의 최신
  프레임을 JSON으로 내보내고, `assets/app.js`가 200 ms 간격으로 폴링해서
  히트맵을 그립니다.

### 2.5 시각 자료

같은 흐름을 애니메이션으로 본 것이 프로젝트 루트의 `tof3-signal-flow.html`
입니다 — I²C 읽기 → Bridge 알림 → HTTP 폴링까지 패킷이 실제로 움직이는

## 3부. 전원(전류/GND) 문제 진단

버스를 분리한 뒤에도 센서 3(혼자 쓰는 `Wire2`)이 간헐적으로 "값이 나오다
꺼지는" 현상이 재현돼서, 로그를 다시 파봤습니다.

### 3.1 오류 메시지가 알려주는 것

```
[ToF 3] error: No measurement for 5 seconds (code=3)
```

`sketch.ino:213-214`:

```cpp
if (!ready) {
  if (millis() - sensor.lastFrame > 5000) fail(i, "No measurement for 5 seconds", 3);
}
```

이건 `vl53l8cx_check_data_ready()`(I²C 레지스터 읽기) 자체는 계속 성공하는데,
센서 내부가 5초 넘게 "새 측정값 없음"만 돌려준다는 뜻입니다. **통신선은
멀쩡한데 센서 칩 내부의 레인징(측정) 엔진만 멈춘 상태** — 전형적으로 칩에
전원이 순간적으로 부족해져서 내부 동작은 멎었지만, 훨씬 저전력인 I²C 응답
회로만 살아있을 때 나오는 증상입니다. 이전에 보던 `Data-ready read failed`
류(전송 자체가 깨지는 오류)와는 성격이 다릅니다.

### 3.2 결정적 증거: 완전히 분리된 버스인데 타이밍이 겹칩니다

`No measurement for 5 seconds`가 로그에 5번 나오는데, **5번 전부** 다음
패턴 직후에 발생했습니다:

```
[ToF 1] error: No sensor at default/assigned address ...   ← 센서 1 완전 무응답 반복
[ToF 1] error: No sensor at default/assigned address ...
[ToF 3] error: No measurement for 5 seconds (code=3)       ← 바로 이 순간 센서 3도 멈춤
```

센서 1·3은 이제 SDA/SCL을 공유하지 않습니다(§2.1). 그런데도 동시에
흔들린다는 건, 버스 문제로는 설명이 안 되고 **둘이 공유하는 유일한
것 — 전원(VCC)·GND** 쪽 문제라는 뜻입니다.

### 3.3 GND도 용의선상입니다

GND는 "0V 기준선"이 아니라 전류가 실제로 돌아가는 **선**이라 저항이 0이
아닙니다. 한 센서가 전류를 확 끌어 쓰는 순간(펌웨어 업로드 등) 그 전류가
공유 GND 구간을 타고 돌아가면서 그 구간에 전압강하(그라운드 바운스)가
생기고, 다른 센서 입장에서는 자신의 "0V 기준점"이 순간적으로 들뜹니다.
I²C 신호 판정 기준이 전부 GND라, 기준점이 흔들리면 SDA/SCL 선 자체는
멀쩡해도 오작동할 수 있습니다. **VCC 처짐과 GND 바운스는 사실상 같은
문제(공유 전원 경로의 임피던스 부족)의 두 얼굴**입니다.

**측정 시 주의**: 멀티미터 검은 탐침을 UNO Q의 먼 GND가 아니라 **그
센서 자신의 GND 핀**에 대고, 빨간 탐침을 그 센서의 VCC 핀에 대야 그 칩이
실제로 겪는 전압차가 보입니다. 펌웨어 로딩 순간(`checking→initializing`)
값이 얼마나 떨어지는지 확인하세요.

### 3.4 "5V로 바꾸면?" — 칩 자체 전원 스펙 확인 결과

사용자가 제공한 VL53L8CX 데이터시트 발췌: 칩은 **1.8V 코어 + 3.3V AVDD +
1.2~1.8V IOVDD**, 세 레일이 따로 필요합니다. IOVDD(I²C 신호 레벨)가
1.2~1.8V라 5V는 물론 3.3V도 칩 핀에 그대로 물리면 안 되는 스펙입니다.

다만 지금 모듈은 이미 UNO Q의 3.3V LPn 신호로 정상 식별되고 3.3V I²C로
통신해온 이력이 있어(§0부 #1), **레귤레이터+레벨시프터가 내장된
브레이크아웃 보드**로 판단됩니다 — 모듈 종류 자체는 문제가 아니고, 원인은
여전히 전류/GND 쪽입니다.

### 3.5 전원을 병렬로 묶지 말 것

"UNO Q 3.3V + 별도 외부 3.3V 전원을 같은 지점에 같이 연결"은 **금지**입니다.
두 레귤레이터의 실제 출력 전압은 미세하게 달라서, 높은 쪽이 낮은 쪽으로
전류를 역으로 밀어 넣습니다(백피드) — 낮은 쪽이 과전류 보호로 껐다 켰다를
반복하거나(지금 겪는 증상을 오히려 더 만듦), 최악의 경우 고장 날 수
있습니다. 외부 전원을 쓰려면 **UNO Q 3.3V는 그 레일에서 빼고 외부 전원
하나만** 연결하고, GND만 서로 공통으로 묶으세요.

### 3.6 USB 입력 전원(컴퓨터 vs 고속 충전기)

3.3V는 보드 위 레귤레이터가 5V USB 입력을 낮춰 만드는 값이라, 입력
전압의 "깨끗함"보다 **입력 전류 한도**가 관건입니다. 컴퓨터 USB 포트는
500~900mA로 제한되는 경우가 흔하고, 고속 충전기는 더 여유가 있을 수
있습니다. 단, USB-PD 협상형 충전기는 기기가 협상하지 않으면 오히려
전류가 안 늘 수 있어 **"5V 기준 전류(예: 5V⎓2A)"가 명시된 충전기**를
권장했습니다. 무료·간단한 테스트라 시도를 제안했고, 같은 오류율 명령으로
전/후 비교 예정입니다.

### 3.7 확인·해결 우선순위 (남은 선택지)

1. **충전기 교체 테스트** — 결과 대기 중, 가장 간단.
2. **그 센서 자신의 GND 기준 VCC-GND 실측** — 펌웨어 로딩 순간 전압 강하
   확인 (§3.3).
3. **외부의 넉넉한 3.3V 전원으로 센서 레일 전체 교체** — UNO Q 3.3V와
   병렬 연결 금지(§3.5), GND만 공통.
4. **센서 1·2 중 하나의 풀업 저항 물리적 제거** — §풀업 확인 방법 참고,
   버스 분리·클럭 조정으로는 해결 안 된 것으로 확인됨(§0부 #7).
