`README.md`가 "지금까지 있었던 일"을 시간순으로 기록한 문서라면, 이
문서는 **지금 이 순간 실제로 동작하는 코드가 정확히 뭘 하는지**만

## 1. 전체 그림

```
[ToF 센서 3개] --I²C--> [UNO Q MCU, sketch.ino]
                              │ Bridge(RPC)
                              ▼
                        [UNO Q MPU, python/main.py]
                              │ 5Hz로 갱신, 웹서버(WebUI 브릭)
                              ▼
                  GET http://localhost:7000/api/status
                              │ 0.2초마다 HTTP 폴링
                              ▼
              [Docker 컨테이너: ros_jazzy, tof3_bridge 노드]
                              │ ROS2 토픽 (DDS)
                              ▼
              /tof/sensor{1,2,3}/grid   (MarkerArray)
              /tof/sensor{1,2,3}/range  (Range)
              /tf_static                (센서 3개 좌표축)
                              │ Wi-Fi 네트워크
                              ▼
                   [Windows WSL2, rviz2]  ← 8×8 색상 격자 3개로 시각화
```

**두 개의 독립된 프로그램**이 이어져 있다는 게 핵심입니다:

1. `../tof3-i2c/` — 원래부터 있던 Arduino App. I²C로 센서를 읽고
   `/api/status`라는 웹 주소로 값을 내보낼 뿐, ROS2를 전혀 모릅니다.
2. `ros2_ws/src/tof3_bridge/` — 이번에 새로 만든 ROS2 패키지. `/api/status`를
   그냥 **웹 요청으로 읽어와서** ROS2 토픽으로 다시 포장해 내보낼 뿐,
   센서나 I²C를 전혀 모릅니다.

이 둘은 `http://localhost:7000/api/status`라는 URL 하나로만 연결돼
있어서, **둘 다 따로 실행해야** 전체가 동작합니다(자세한 이유는
`README.md` §1-4 참고).

## 2. `tof3_bridge` 패키지 구성

```
ros2_ws/src/tof3_bridge/
├── package.xml              # 의존성 선언 (rclpy, sensor_msgs, visualization_msgs, tf2_ros, python3-requests 등)
├── setup.py / setup.cfg     # ament_python 빌드 설정
├── resource/tof3_bridge     # ament 패키지 마커(빈 파일)
├── launch/
│   └── bringup.launch.py    # `ros2 launch tof3_bridge bringup.launch.py` 한 줄로 실행
└── tof3_bridge/
    ├── __init__.py
    └── tof_bridge_node.py   # 실제 로직 전부 (아래 §3)
```

빌드하면 `ros2_ws/install/`, `build/`, `log/`가 생기는데, 이건 매번
`colcon build`가 만들어내는 산출물이라 **소스가 아닙니다**(지워도
다시 빌드하면 복구됨).

## 3. `tof_bridge_node.py` — 노드 하나가 하는 일

### 3-1. 파라미터

| 이름 | 기본값 | 의미 |
|---|---|---|
| `status_url` | `http://localhost:7000/api/status` | 데이터를 읽어올 주소 |
| `near_mm` | 50.0 | 색상 매핑의 "가까움"(빨강) 기준 |
| `far_mm` | 2000.0 | 색상 매핑의 "멂"(파랑) 기준 |
| `cell_size_m` | 0.04 | 격자 한 칸의 크기(가로/세로) |
| `max_range_m` | 4.0 | `Range` 메시지의 최댓값 |
| `poll_period_s` | 0.2 | `/api/status`를 얼마나 자주 읽을지(센서 자체 주기 5Hz와 동일) |

`launch/bringup.launch.py`에서 `status_url`만 launch 인자로 바꿀 수
있게 해뒀고, 나머지는 필요하면 `ros2 run tof3_bridge tof_bridge_node
--ros-args -p near_mm:=100.0` 식으로 실행 시 덮어쓸 수 있습니다.

### 3-2. 발행하는 토픽 (센서 1개당)

| 토픽 | 타입 | 내용 |
|---|---|---|
| `/tof/sensor{N}/grid` | `visualization_msgs/MarkerArray` | 8×8 격자 시각화 (아래 §3-4) |
| `/tof/sensor{N}/range` | `sensor_msgs/Range` | 그 센서의 유효값 중 최솟값(m) — 나중에 장애물 회피 로직에서 바로 쓸 수 있게 남겨둠 |
| `/tf_static` | (자동) | `base_link → tof_sensor{N}_frame` 좌표축 3개 |

### 3-3. 데이터 흐름 (`poll()` → `_publish_sensor()`)

1. `poll()`이 0.2초마다 `requests.Session.get(status_url)`로 JSON을
   가져옵니다. 실패하면(연결 끊김 등) 5초에 한 번만 경고 로그를 찍고
   이번 주기는 조용히 건너뜁니다(`throttle_duration_sec=5.0`) — 그래서
   데이터 소스가 꺼져 있어도 노드 자체는 안 죽고 계속 재시도합니다.
2. JSON의 `sensors` 배열을 돌면서, 각 센서(`id` 0~2)마다
   `_publish_sensor(idx, sensor)`를 부릅니다.
3. `_publish_sensor`가 그 센서의 `distance_mm`(64개, mm 또는 null) 배열을
   가지고 `MarkerArray`와 `Range`를 만들어 발행합니다.

### 3-4. `MarkerArray`(격자) 구성 — "위치가 아니라 색으로 거리 표현"

처음엔 `PointCloud2`로 각 zone을 각도·거리에 따라 3D 공간에 투영하는
방식으로 만들었는데, 점들이 흩어져 보여서 "8×8 패널"처럼 안 보이는
문제가 있었습니다. 그래서 `jungju.md`(참고 문서, 시각화 기법만 차용)와
원래 웹 UI(`../tof3-i2c/assets/app.js`의 히트맵)와 같은 방식으로
바꿨습니다 — **64칸을 평평한 고정 격자에 배치하고, 거리값은 위치가
아니라 색으로만 표현**합니다.

한 센서의 `MarkerArray`는 마커 66개로 구성됩니다:

- **`CUBE_LIST` 1개**(`ns={센서}_cells`, id=0): 64개 정육면체가 한
  마커 안에 들어있음. 각 칸의 위치는
  `x=(col-3.5)*cell_size`, `y=(row-3.5)*cell_size`(평면 격자, row0=위쪽),
  색은 `distance_to_color()`가 계산(아래).
  칸 크기는 `cell_size*0.82`로, 칸 사이에 18% 여백을 둬서 서로 안 붙어
  보이게 함(처음엔 95%로 뒀다가 여백이 거의 안 보여서 조정함).
- **`TEXT_VIEW_FACING` 64개**(`ns={센서}_labels`, id=1~64): 각 칸
  중심 바로 위(z=0.02)에 그 칸의 거리(mm) 숫자를 표시. 측정 실패는
  `—`.
- **`TEXT_VIEW_FACING` 1개**(`ns={센서}_title`, id=0): 격자 한쪽
  끝(`y=-(half+1)*cell_size`)에 `"TOF{N}  유효 X/64"` 제목.

`lifetime`을 0(무제한)으로 뒀기 때문에, 다음 갱신이 올 때까지 마커가
화면에 유지됩니다(같은 ns/id로 다시 발행하면 rviz2가 알아서 내용만
갱신).

### 3-5. 색상 매핑 (`distance_to_color()`)

```python
t = (mm - near_mm) / (far_mm - near_mm)   # 0.0~1.0로 정규화, 범위 밖은 clamp
h = t * 240 / 360                         # 0(빨강)~240도(파랑)를 colorsys 입력 범위로 변환
r, g, b = colorsys.hsv_to_rgb(h, 1.0, 1.0)
```

`mm`이 `None`(측정 실패)이면 회색(`0.6,0.6,0.6`)을 반환합니다.
`near_mm=50`, `far_mm=2000`은 원래 웹 UI의 기본 색상 범위(0~2000mm)와
맞춘 값입니다.

### 3-6. 좌표축(TF) — `_publish_static_frames()`

```python
offsets_y = (0.45, 0.0, -0.45)  # 센서 1/2/3
```

`base_link`를 기준으로 센서 3개의 프레임(`tof_sensor{N}_frame`)을 Y축
방향으로 0.45m씩 떨어뜨려 한 번만(`StaticTransformBroadcaster`) 발행합니다.
회전은 없음(정면 그대로).

> ⚠️ **이 위치·회전은 전부 임시값입니다.** 실제 로봇에 센서를 붙인
> 물리적 위치·각도가 아닙니다 — 지금은 그냥 패널 3개가 화면에서 서로
> 안 겹치게 벌려둔 것뿐입니다. 실제 장착 위치가 정해지면 이 함수의
> `translation.x/y/z`와 `rotation`을 반드시 실측값으로 바꿔야 합니다.
> (패널 폭이 `7*cell_size`(기본 0.28m)라서, 간격을 그보다 좁게 두면
> 옆 패널과 겹쳐 보입니다 — 0.3m로 뒀다가 겹쳐 보여서 0.45m로 키운
> 적 있음.)

## 4. 실행 방법 (요약 — 자세한 건 `README.md` §7·§8)

```sh
# ① UNO Q 호스트 터미널 (컨테이너 밖)
arduino-app-cli app start /home/arduino/ArduinoApps/tof3-i2c

# ② 컨테이너 안 (docker exec -it ros_jazzy bash로 진입 후)
source /opt/ros/jazzy/setup.bash
source /root/ros2_ws/install/setup.bash   # 빌드 후에만 존재
export ROS_DOMAIN_ID=30
ros2 launch tof3_bridge bringup.launch.py

# ③ WSL2에서 (ROS_DOMAIN_ID=30 맞추고)
rviz2   # Fixed Frame = base_link, Add → By topic → /tof/sensor{1,2,3}/grid
```

매번 `source`/`export`를 반복하지 않으려면 컨테이너 안 `~/.bashrc`에
등록해두면 됩니다(`README.md` 참고).

## 5. 알려진 제한사항 / 임시값 정리

| 항목 | 상태 |
|---|---|
| 센서 좌표축 위치·회전(§3-6) | 임시값 — 실제 장착 위치로 교체 필요 |
| `near_mm`/`far_mm`(50~2000mm) | 웹 UI 기본값과만 맞춘 것, 실제 용도에 맞게 조정 가능 |
| 데이터 소스가 `/api/status`(HTTP) | RP2350 전환 전까지의 임시 경로. 전환 시 `poll()`만 시리얼 읽기로 교체, 그 아래(`_publish_sensor` 이하)는 그대로 재사용 가능 |
| 풀업 저항·전원/GND 문제 | **아직 근본 해결 안 됨** — RP2350로 옮긴다고 자동으로 해결되지 않음, `README.md` §5.1과 `../tof3-i2c/tof3-i2c-notes.md`의 체크리스트를 재배선 시 그대로 적용해야 함 |
| `turtlebot3-node`/OpenCR 연동 | 아직 코드 없음, `README.md` §5.5에 설치 명령만 확인된 상태 |
